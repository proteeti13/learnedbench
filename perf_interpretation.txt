================================================================
Hardware Performance Analysis: ZM-Index vs RSMI
Point Queries on Wiki-Vote Graph Dataset
================================================================

OVERVIEW
--------
ZM-Index achieves 6.5x lower mean query latency than RSMI on the same dataset
(0.22 µs vs 1.46 µs at comparable scales). The perf counters reveal the
hardware-level reasons: ZM-Index is memory-friendly and compute-cheap per
query; RSMI is memory-intensive and compute-heavy.

================================================================
1. CACHE EFFICIENCY
================================================================

L1 Data Cache Miss Rate:
  ZM-Index:  0.32%   (4.8M misses / 1.51B loads)
  RSMI:     11.76%  (11.8B misses / 100.4B loads)
  => RSMI has 37x higher L1 miss rate

Last-Level Cache (LLC) Miss Rate:
  ZM-Index:  9.30%   (38K misses / 413K loads)
  RSMI:     35.83%  (620M misses / 1.73B loads)
  => RSMI has 3.9x higher LLC miss rate

LLC misses per query (upper bound):
  ZM-Index:  0.38 LLC misses/query
  RSMI:      6,199 LLC misses/query
  => RSMI incurs ~16,000x more LLC misses per query

WHY: A ZM-Index point lookup is a two-step pipeline:
  (a) Morton encode the query point: deterministic bit-interleaving using the
      PDEP instruction — no memory access at all.
  (b) PGM linear model prediction: evaluate a single piecewise-linear segment
      (one multiply + one add), then binary search ±64 positions in a sorted
      64-bit array. The PGM segments fit in L1 cache; the binary search access
      pattern is predictable.

  An RSMI point lookup traverses a 3-level hierarchy of neural networks:
  root model → partition model(s) → leaf model. Each level loads weight
  matrices from different memory locations (non-contiguous). At 100K data
  points, the partition models themselves may not fit in L1/L2 cache, causing
  frequent LLC misses. At 1M points the weight matrices are larger still.

================================================================
2. INSTRUCTION PIPELINE EFFICIENCY (IPC)
================================================================

Instructions Per Cycle:
  ZM-Index:  2.41 IPC
  RSMI:      0.46 IPC

ZM-Index achieves 5.2x higher IPC. An IPC of 2.41 indicates the CPU is
well-utilised — multiple independent instructions execute per clock (OOO
execution, SIMD). An IPC of 0.46 means the CPU is stalled more than half the
time, waiting on memory (LLC misses cause stalls of 40-200 cycles each on
modern x86).

Instructions per query:
  ZM-Index:  ~56,384 instructions/query
  RSMI:      ~3,307,425 instructions/query
  => RSMI executes 58.7x more instructions per query

Note: these counts include the build phase (which dominates RSMI's wall time).
The actual per-query instruction count for pure queries is lower, but the
qualitative gap remains: RSMI's neural network inference (matrix multiply,
activation functions, argmax) is inherently instruction-heavy compared to
ZM-Index's arithmetic + binary search.

================================================================
3. BRANCH PREDICTION
================================================================

Branch miss rate:
  ZM-Index:  0.64%
  RSMI:      0.71%
  => Comparable rates — this is NOT the differentiator

Branch misses per query (total / 100K):
  ZM-Index:  73.8 branch misses/query
  RSMI:      4,389 branch misses/query
  => RSMI has 59x more absolute branch misses per query

The branch miss RATE is similar (0.64% vs 0.71%) but RSMI executes ~53x more
branches in absolute terms, so the total number of mispredictions (and their
associated pipeline flush penalties) is far higher for RSMI. ZM-Index's
binary search branches are predictable (compare-and-advance); RSMI's tree
routing branches (which child model to enter at each level) are data-dependent
and harder to predict.

================================================================
4. CONNECTION TO OBSERVED LATENCY
================================================================

Observed latency ratio: 1.457 µs / 0.2245 µs = 6.49x (RSMI slower)

The hardware counters explain this through three compounding effects:

(a) Memory stalls dominate RSMI:
    RSMI has 11.76% L1 miss rate vs 0.32% for ZM-Index. Each LLC miss stalls
    the pipeline for ~40-100 ns on typical x86 (main-memory latency). With
    6,199 LLC misses per query × ~50 ns = ~310 µs of potential stall per query.
    In practice the CPU overlaps some of this via OOO execution (explaining why
    measured latency is 1.46 µs, not 310 µs), but memory pressure clearly
    limits throughput.

(b) Instruction count difference:
    58.7x more instructions per query × lower IPC = dramatically more wall
    time spent in CPU. Neural network inference (dense matrix multiply for
    each level of the index tree) is inherently expensive in instructions
    compared to a single PGM prediction + binary search.

(c) ZM-Index's Z-order linearisation is cache-friendly:
    Z-order curves have good locality: nearby points in 3D tend to map to
    nearby Morton codes, so the binary search touches a spatially compact
    region of the sorted array. This is why L1 miss rate is only 0.32%.
    RSMI's weight matrices are addressed by learned partition boundaries —
    access patterns depend on the query value and the model structure, with
    no spatial locality guarantee across queries.

================================================================
6. RSMI 1M RESULTS — BUILD-SCALE-MATCHED COMPARISON
================================================================

RSMI at 1M data points (same scale as ZM-Index) makes the hardware gap
even more pronounced:

  IPC:           RSMI drops from 0.46 → 0.25 as the 1M model no longer
                 fits in LLC. ZM-Index stays at 2.41 (9.6x advantage).

  LLC miss rate: RSMI rises from 35.83% → 44.40%. Cache references grow
                 17x (6.6B → 122B) while ZM-Index's stay at 2.9M —
                 a 43x difference in absolute cache pressure.

  LLC misses/query: ZM-Index 0.38 vs RSMI 18,251 → 48,000x gap at 1M scale.
                 This is the dominant source of latency: each LLC miss
                 costs ~50-100 ns in main-memory stall time.

  Latency:       ZM-Index 0.22µs vs RSMI 2.40µs → 10.7x gap at 1M.
                 The gap grows with data size (was 6.5x at 100K vs 10.7x
                 at 1M) because RSMI's neural network weights grow with
                 data, progressively overflowing the cache hierarchy.

SCALING BEHAVIOUR CONCLUSION:
  ZM-Index's cache footprint is nearly constant with N — the PGM segments
  and the binary search window (±64 positions = 512 bytes) are always
  tiny relative to L1. RSMI's cache footprint grows with N because more
  data means more partitions, larger weight matrices, and deeper trees.
  This explains why ZM-Index's latency advantage widens at larger scales.

================================================================
CAVEAT: The perf counters cover the full program (data load + build + queries).
Build time dominates RSMI runs (49s at 100K, 1170s at 1M). Per-query
estimates are upper bounds. However, the qualitative conclusions are robust
and consistent across both RSMI runs: RSMI's neural network architecture
requires fundamentally more memory traffic and instructions per query than
ZM-Index's Morton-encode + PGM-predict + binary-search pipeline.
